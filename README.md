# AML Collusion Detection

Money laundering usually isn't one suspicious payment. It's a group of accounts passing money around
in fan-outs, cycles and scatter-gather patterns, which you can only see by looking at who pays whom.
In this project I tried to find out how much that payment graph actually helps compared with a
strong model that scores each transaction on its own.

I used IBM's synthetic AML dataset (HI-Small: 5 million transactions, 515k accounts), built
leakage-free features, compared XGBoost, graph features, a GraphSAGE GNN and some unsupervised
methods, and then served the best model through a FastAPI service with drift monitoring.

## Results

Trained on 1–6 Sep, tuned on 6–8 Sep, tested once on 8–10 Sep (about 1M payments, 1,143 of them
laundering). Every feature only uses data from before the payment it describes.

| Model | Test PR-AUC | Laundering caught when 1% of normal payments are flagged | Alerts on the test period |
|---|---|---|---|
| Random | 0.001 | 1% | |
| XGBoost, account features | 0.558 | 82.6% | 20,084 |
| XGBoost + graph features (served model) | **0.567** | 83.2% | **13,979** |
| GraphSAGE | 0.446 | 78.7% | 21,111 |
| GraphSAGE + XGBoost ensemble | 0.555 | **84.6%** | 16,847 |
| Isolation Forest + communities (no labels) | 0.005 | 2.3% | 14,714 |

What I took away from it:

- Graph features gave a small but real improvement in ranking. The bigger effect was practical: the
  alert threshold held up better on new data, so the model raised 30% fewer alerts for almost the same
  recall.
- GraphSAGE on its own was clearly worse than XGBoost, but it catches different cases. Averaging the
  two caught 1.4 points more laundering at the same alert volume.
- About 13% of the laundering can't be found by any of these models. It's cheque, cash and credit card
  payments sent by a handful of very large accounts, and nothing in the data separates it from their
  normal traffic.
- Without labels, very little is caught at a realistic alert budget. But community detection is
  still useful once you have one alert: the flagged account's community contains about half of the
  other accounts in the laundering scheme, around 50 times more than chance.

## Data

[IBM Transactions for Anti Money Laundering](https://www.kaggle.com/datasets/ealtman2019/ibm-transactions-for-anti-money-laundering-aml)
on Kaggle. It's synthetic, generated by simulating banks, companies and individuals, with laundering
injected as known patterns. I used the HI-Small files:

- `HI-Small_Trans.csv`: 5,078,345 transactions with amounts, currencies, payment format and label
- `HI-Small_accounts.csv`: accounts and the entity that owns them
- `HI-Small_Patterns.txt`: laundering transactions grouped into named schemes

The data isn't in this repo (the transactions file alone is ~475 MB). Download it and put the three
files in `data/raw/`.

A few things in the data needed handling. After 10 Sep the simulation stops generating normal
traffic, so the last 1,108 transactions are mostly laundering; I cut them, otherwise they would all
land in the test set and inflate the results. Bank codes have leading zeros in one file and not the
other, so accounts are identified by a normalised `bank_account` key. There's no exchange-rate table,
so currency rates are estimated from the cross-currency payments themselves.

## How it works

The project is split into seven steps. Each step is a function in `src/aml/`, can be run from the
command line, and has a notebook that walks through it.

1. **Cleaning**: account IDs, USD amounts, a time-based 60/20/20 split.
   ([notebook](notebooks/01_data_exploration.ipynb))
2. **Account features**: 75 features per payment, covering activity over the last hour, day and all history,
   amounts, counterparties, and whether the two accounts have paid each other before. Unit tests check
   them against a brute-force version and check that deleting future rows changes nothing.
   ([notebook](notebooks/02_feature_engineering.ipynb))
3. **XGBoost baseline**: four settings, the best one picked on validation, alert thresholds fixed on
   validation. ([notebook](notebooks/03_baseline_xgboost.ipynb))
4. **Graph features**: 20 more features, including exact counts of 2–3 hop cycles and scatter-gather routes,
   new counterparties in the last hour/day, PageRank and connected components from daily snapshots.
   ([notebook](notebooks/04_graph_features.ipynb))
5. **GNN**: GraphSAGE in PyTorch Geometric with message passing in both directions, compared with the
   same network without the graph layers and with an ensemble. Training uses 2-hop mini-batches so it
   runs on a laptop CPU. ([notebook](notebooks/05_gnn.ipynb))
6. **No labels**: Isolation Forest and Leiden community detection, evaluated against the labels and
   the named laundering schemes. ([notebook](notebooks/06_unsupervised.ipynb))
7. **Production**: a FastAPI scoring service, a drift monitor and a Dockerfile.
   ([notebook](notebooks/07_production.ipynb))

![Laundering rate by relationship between sender and receiver](reports/figures/06_relationship_signals.png)

Model comparisons use bootstrap confidence intervals that resample whole hours of the test set,
because laundering comes in bursts and neighbouring payments aren't independent. All results are
in `reports/metrics_step*.json`.

The GNN results move a bit between runs because PyTorch on CPU isn't bit-for-bit reproducible. An
earlier run gave the ensemble +2.2 points instead of +1.4. The XGBoost steps are fully reproducible.

## Serving and monitoring

The served model is the XGBoost with graph features. The tricky part of serving it is that a
payment's features depend on everything that happened before it, so the service keeps a feature
store built from the transaction history with the same code as the training pipeline. I checked
that 3,200 real test payments sent as raw records get exactly the same features and scores as in
training.

A payment is scored in about 37 ms and each alert comes with the three features that pushed its
score up. The service also tracks the recent alert rate against the 1% budget and the shift in the
score distribution (PSI).

![Daily alert rate of the served model](reports/figures/15_daily_alert_rate.png)

On the test period the alert rate stays around the expected 1.1% until 10 Sep, when the simulation
winds down and it doubles. Replaying the test period through the monitor, it flags this from 10 Sep
04:00 and ignores the one-hour blips at midnight.

Known limits: payments scored by the service are only added to the feature store when it's rebuilt
(e.g. nightly), and a real deployment would also need authentication, stored alerts and retraining
on new labels.

## Running it

Python 3.10+. From the project folder:

```bash
python -m venv .venv
.venv\Scripts\activate              # macOS/Linux: source .venv/bin/activate
pip install torch --index-url https://download.pytorch.org/whl/cpu
pip install -r requirements.txt
pip install -e .
pytest -q
```

Run the whole pipeline (about 2 hours on a laptop, stops at the first error):

```bash
python main.py all
python main.py all --skip-gnn       # skips the GNN, the slowest step
python main.py all --from baseline  # resume from a given step
```

Each step can also be run on its own: `clean`, `features`, `baseline`, `graph-features`,
`graph-model`, `gnn`, `unsupervised`, `build-store`, `monitor`. See `python main.py -h`.

Start the API and open http://127.0.0.1:8000/docs to score payments from the browser:

```bash
python main.py serve
```

Or with Docker, after `python main.py build-store`:

```bash
docker build -t aml-scoring .
docker run -p 8000:8000 -v "${PWD}/data/processed:/data" aml-scoring
```

Example request for `POST /score`:

```json
{"payments": [{"timestamp": "2022-09-08 16:12", "from_bank": "46479", "from_account": "811645E20",
  "to_bank": "20861", "to_account": "811646190", "amount_paid": 13731.57,
  "payment_currency": "Euro", "amount_received": 13731.57, "receiving_currency": "Euro",
  "payment_format": "ACH"}]}
```
